degradation_rules:
  - case: version matches
    restored: main_progress, chapter_snapshots, current_city_state, both knowledge id lists
    discarded: nothing
    player_sees: "Save loaded." and, when a snapshot is malformed, which stages cannot be replayed
    chapter_select: available
  - case: version does not match
    restored: main_progress only
    discarded: chapter_snapshots and current_city_state
    player_sees: "Save version N does not match this build's version M. Progress between stages was kept; the stage snapshots and the live city state were discarded, so the current stage restarts from its beginning and chapter select is unavailable."
    chapter_select: unavailable
  - case: file corrupt or unparseable
    restored: nothing
    discarded: nothing is deleted; the file stays on disk exactly as found
    player_sees: "The save file is not valid JSON. It has been left on disk untouched and a new run has started."
    chapter_select: unavailable
  - case: no file at all
    restored: nothing
    discarded: nothing
    player_sees: "No save file yet. Starting a new run."
    chapter_select: unavailable

the_float_trap: |
  save_version is written as the integer 1 and reads back as the float 1.0,
  because Godot's JSON parser returns every number as a float. The comparison
  casts through float and then to int rather than comparing types. A strict
  integer equality here would have treated every healthy save as a mismatch and
  fired the degradation path on a perfectly good file. This was reported in
  docs/coord/done/T-26.md before this task began, and is the first thing the
  version check does.
first_stage_snapshot_ruling: |
  Three documents disagreed about which stages get a snapshot. The T-26 prompt
  says every started stage, table F2 of docs/CARRYOVER_SPEC.md defines writes only
  for the three stages that receive carryover, and the T-28 prompt says any
  completed stage may be replayed. The first stage falls in the gap: it has no
  predecessor, so it receives no carryover.
  An earlier draft of the snapshot validity rule required all three table F1
  carryover fields of every snapshot, which would have made the tutorial stage
  permanently unreplayable while looking like a data integrity check.
  The project owner ruled that stage one is replayable. The rule now requires the
  carryover fields only of a stage that actually receives carryover, and judges
  the first stage on completeness alone. Which stage is first comes from
  progress.initial.current_stage_id rather than being named in the script.
