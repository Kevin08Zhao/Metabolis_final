how_to_confirm_the_pause_is_real: |
  This is the part of the acceptance worth reading, because "the interface froze"
  and "settlement stopped" look identical on screen.

  The pause has two mechanisms because the requirement has two halves.
  get_tree().paused stops timers and every processing node. That alone is the
  weak half: the resource loop is not driven by _process, it is driven by
  ResourceTick.advance_time(elapsed_seconds, ...) being handed a number. A frozen
  UI would leave that number accumulating and hand over the whole paused interval
  in one lump the moment the archive closed.

  So the script exposes elapsed_for_settlement(delta), the seam a tick driver
  calls instead of using its own delta. While the archive is open it returns zero
  and adds the delta to withheld_seconds() instead - discarded, not banked.

  Verified against a real ResourceTick, not a stand-in:
    ten unpaused seconds      resource totals moved by 8.626040
    thirty paused seconds     resource totals moved by 0.000000 exactly
    withheld_seconds()        30.0
    first tick after closing  moved 0.770708
    an ordinary tick after    moved 0.770636

  The last two lines are the ones that rule out catch-up. Had the paused interval
  been banked, the first tick after closing would have moved about thirty times
  an ordinary tick. It moved 1.0001 times.

  By hand: open an organ archive, watch any resource readout for thirty seconds,
  close it, and watch the next tick. If the value jumps on the tick after closing
  rather than stepping normally, the pause was cosmetic.
