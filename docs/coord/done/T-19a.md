interface_changes: |
  Adds class MinigameRuntime (Node) at src/minigame/minigame_runtime.gd.
  Entry:      begin(minigame_id, stage_id, goal_key := &"") -> bool
  Timing:     advance_time(seconds); _process drives it while RUNNING
  Goal:       report_progress(completed_units); completion_accuracy();
              completion_efficiency(); use_hint()
  Exit:       skip() -> bool
  Failure:    fail(reason_code) -> bool; retry() -> bool
  Read-only:  state(), resolution(), resolution_id(), stars(), rating_detail(),
              pending_reward(), elapsed_sec(), time_limit_sec(),
              difficulty_tier(), difficulty_parameters(), hint_usage_count(),
              consecutive_failures(), last_failure_reason()
  Signal:     run_resolved(minigame_id, resolution)
  enum State { IDLE, RUNNING, SETTLED, FAILED }
  enum Resolution { PENDING, SKIPPED, COMPLETED } with RESOLUTION_IDS giving the
  spelling stored in ChapterData.minigame_resolution.

  A prototype supplies gameplay only. It calls report_progress as its own rules
  dictate, use_hint when the player opens a hint, and fail when its own rule is
  broken. It never calls _settle and never touches the clock.

  Callers apply pending_reward() during Phase.RESOURCE_SETTLEMENT, as the
  resolve_optional_minigame row of docs/GAME_RULES.md requires. The runtime does
  not write to ChapterData; a caller listening to run_resolved updates
  minigame_resolution itself.
judgment_calls: |
  Two points the specification does not settle outright are recorded here rather
  than left implicit.

  A completed run at zero stars still settles one knowledge badge. Table M4 scales
  the star multiplier across the three spendable components only, and
  docs/CONTEXT.md makes badges a counter that is never spent, so treating them as
  a participation count rather than a performance reward follows the tables as
  written. A skipped run settles nothing at all. If the intent was that badges
  scale too, M4 needs a line and this runtime needs one change.

  A timeout records the configured reason code "timeout" while still settling as
  a rated outcome. minigames.failure.reason_codes lists timeout alongside
  target_not_reached and chain_broken, but table M1 states a timeout is an
  ordinary rating outcome and not a failure category. Both hold here: reason codes
  explain why a run ended, and only a prototype calling fail() constitutes failure.
